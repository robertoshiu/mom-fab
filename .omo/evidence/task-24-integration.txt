#1 Event-river chip click → correct module switch + entity highlight
------------------------------------------------------------------------
Root-cause fixed: the event river lives in the topbar, NOT inside the
router's #content container, so its bubbling `river:navigate` CustomEvent
never reached the router's container listener — chip navigation was a no-op.
Bridged via the river's onNavigate → router.navigateFromEvent(detail), which
routes by EVENT_ROUTING and stamps a one-shot ctx.focus payload (chip's event
payload, with lotId/equipmentId/poId/recipeId/type hoisted).

Steps: router.set('spc'); click a lot.start chip (●L-038 Lot Start).
Result:
  { "active": "mes", "selectedRow": "L-038" }
PASS — switched SPC→MES via EVENT_ROUTING AND highlighted lot L-038's row
(tr.mes-row-selected). Screenshot: task-24-cross-module.png.

#2 Cross-module data flow: MES Hold → WIP shows hold on next update
------------------------------------------------------------------------
Root-cause fixed: app.js's lot-lifecycle subscriber blindly overwrote
lot.status from skeleton events, clobbering a MES Hold back to running on the
next step.transition. (a) app.js now guards status writes behind
state.suppressOverrides (terminal overrides always win; hold wins until its
`until` tick). (b) WIP's gantt now consults suppressOverrides (the same
authoritative source MES uses) instead of lot.status alone.

Steps: MES select L-005 → Hold → advance ticks → router.set('wip').
Result:
  Hold:   { "status": "hold", "override": { "status": "hold", "until": 57 } }
  In WIP: { "active":"wip", "l005_status":"hold", "tick":33, "dangerBlocks":1 }
PASS — L-005 stays hold across ticks; WIP renders exactly one danger-toned
(hold) bar (label "<id> · <group> · HOLD"); chart-kit statusColor('hold')→danger.
